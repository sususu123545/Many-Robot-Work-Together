## 车端切换与回退原则

1. 先备份地图、校准、原始/已修改源码及 systemd 启动链；有备份不等于已验证回退。
2. 先无设备模拟，再轮子架空单项测试，再低速有人看护落地测试。
3. 切换时先关闭旧硬件占用与旧自动任务，仅启动一个驱动。
4. 机械臂不能自动恢复旧脉冲姿态；姿态显示默认值与实际伺服命令严格分离。
5. 每项成功后才逐步替换 rosbridge、网页和启动编排；最终切换前不宣称 ROS 2 全车可用。
6. 失败先停止新自动控制与硬件驱动，再按备份恢复旧服务，不直接删掉旧容器或地图。

此文档中的步骤是后续验收要求，不表示已经执行。

实测证明旧的全负计数前进假设不适用于当前板端回读。ROS 2 改为：

```text
c[i] = delta[i] * metres_per_pulse * encoder_channel_signs[i]
dx   = (c[0] - c[1] - c[2] + c[3]) / 4
dy   = (c[0] + c[1] + c[2] + c[3]) / 4
dyaw = (c[0] - c[1] + c[2] - c[3]) / (4 * (a + b))
```

分别保留四个编码器通道符号与三个车体轴符号，仅允许 +/-1。
新单元测试包含三组真实回读、组合平移/旋转逆解、通道反向和非法配置拒绝；
本机及车端 25 项测试通过。旧 ROS 1 源码及服务配置不改动。
架空测试不能验证地面实际 X/Y 方向、轮滑、行驶距离或转角精度。

### 已修的缺陷：角度换算漏掉符号位

首次试跑**指令被节点拒绝、机械臂完全未动**。节点日志给出原因：
`Step too large; use incremental targets: joint3`（连报3次，对应发出的3条消息）。

根因：`JOINTS` 中 **joint3 的 sign 为 −1（六关节中唯一反相的）**，
而弧度换算写成了 `(target − 500) × tick`，**漏乘 sign**。
于是目标 900 被编码为正角度，节点解码得 `500 + (−1)×1.6755/0.00418879 = **100**`，
与实测 935 相差 835 脉冲，远超 100 的单步上限，整条轨迹被拒。

**这是安全网生效的正面案例**：节点拒绝了会抽到镜像位置的错误指令，而不是执行它。
（此前夹爪操作能成功，纯属 `r_joint` 的 sign 恰好为 +1。）

修复：换算改用 `SIGN × (target − centre) × tick`，并新增**永久的编解码往返断言**——
发布前必须证明 `to_raw(角度) == 目标脉冲`，否则拒绝发布。同类缺陷不可能再溜过。

### 1. 存在性：有实测证据

| 关节 | joint1 | joint2 | joint3 | joint4 | joint5 | r_joint |
|---|---|---|---|---|---|---|

**关键：joint3 = 911，与 14:49:24 走位终点、14:51:30 快照完全一致，六关节一字不差。**
而该臂的自然下垂静止位（已实测记录）是 joint3 ≈ **982**。当前位偏离下垂位
**71 脉冲 ≈ 17°**，且持续 6 分钟以上零漂移。

推理：若保持力矩被卸载，重力条件不变，joint3 必然回落到 982。它没有动。

### 2. 量值：软件读不出来（研究路线关闭）

`ServoBoard` 全部只读接口：`read_id / read_offset / position(0x05) / vin(0x07) /
temp(0x09) / temp_limit(0x3A) / angle_limit(0x32) / vin_limit / torque_state(0x0D)`。

**总线上不存在「负载 / 电流 / 力矩大小」的回读命令。** 因此：

- **「保持力是多少 N·m」无法由任何软件路径获得，只能机械测量**
  （给定臂半径挂已知质量，或弹簧秤拉臂测刚好顶住的力）。
- `0x0D` 只返回**使能状态 0/1**，不是力的大小。
- `0x07` 是**供电电压 mV**，不是输出力矩。代码原注释即写明：
  `A measurement, not proof that the supply/holding torque is healthy.`

### 3. 更糟的一层：运行中的系统连"是否使能"都不知道

`servo_protocol.py` 定义了 `voltage_mv()` 与 `torque_enabled()`，但 `arm_node.py`
的 `poll()` **只读 `position()` + `temperature()`**（源码第 187、189 行）。
全仓搜索确认这两个方法**只被单元测试调用**（`test/test_servo_protocol.py:119/129/137`），
生产路径零调用。→ 当前系统对力矩使能状态**没有任何可观测性**。

### 4. 补读 0x0D / 0x07 的唯一干净路径

串口是**独占**的（`servo_protocol.py:99` 注释：`Exclusive Linux fd; do not allow a
second serial owner.`），arm 节点是 `/dev/rrc` 唯一持有者。

- **不能"旁听"**：0x0D 是查询命令，必须**主动发帧**才能获得回复；在半双工 TTL
  总线上插入外来的帧会与节点轮询相撞，可能被 transport 判为帧不匹配 →
  触发**真实的故障锁存**（现有 `transport.counters.resync = 1` 已记录过此类事件）。
- 唯一干净路径：**短暂停掉 native core 释放串口 → 读 6 舵机的 0x0D + 0x07 →
  立即重启 core**。期间臂不动（停核不会卸力），但会打断一次反馈轮询。
- **需用户显式授权后执行，本次未执行。**

### 5. "停止报文不卸力"的可信度提高（仍是推断）

`servo_protocol.py:303-307` 的 `stop()` 实现是 `03 06 01 02 03 04 05 06`，注释明写
`do NOT unload or enable torque.`。协议另有**独立的** `0x0C` 卸载力矩命令；
既然专门提供了 unload，把 stop 实现成 stop+unload 便显冗余。
→ 可信度提高，**但固件实现未验证，不得当作已验证结论。**

### ⚠️ 遗留未解

- **joint3 停在距目标 8~11 脉冲处，仍无法区分「舵机定位死区」还是「抬升负载上限」。**
  后果同前：若属负载上限，开机自动到位可能从 982（⚠️ **此数已证伪，真实下垂位 ≥1034**）
  出发走到一半就停。
  判别试验（给 joint3 一个更低目标，看能否越过 908）**尚未执行**。
- 走位结束后保留 `enable_arm_motion=true` 的代价：臂关节在域内可被指令
  （rosbridge 9091），此权衡仍需用户持续知情。

#### 三条必须记住的硬约束

1. **部署版 `movement_payload()` 只校验「目标」是否在限位内，不要求「当前位置」有效。**
   而 ROS 节点自身的 move 校验依赖有效当前位置 —— 这正是节点锁存时 ROS 侧无路可走的原因。
   → **总线直驱是绕开 joint3 越界锁存的唯一软件路径**（除物理手抬外）。
2. **部署版 `move()` 拒绝越限目标**：第一条给 1009 直接被
   `ValueError: Invalid servo ID or raw hardware position` 拒掉。
   所以从 1034 出发，**第一条合法目标只能是限位边界 1000**，是个 34 脉冲的跳变。已写进 `next_target()`。
3. **部署版 `servo_protocol` 与本地仓库不是同一构建**：
   - 部署版方法只有 `close/diagnostics/limits/move/position/read/stop/temperature`
     —— **没有 `torque_enabled()` / `voltage_mv()`**（本地仓库有）。
   - 部署版 `read()` 有**命令白名单**：
     `if command not in (0x05, 0x09, 0x32): raise ValueError('Only known read commands with 1..3 attempts allowed')`。
   → **`0x0D`(力矩状态) 与 `0x07`(供电电压) 在这台车上根本读不出来**，
     不是"节点不读"，是**传输层直接禁止**。
   → 只改本地 `servo_protocol.py` 而不同步镜像，会产生"本地有、车上没有"的错觉。

### 6. 因果定性：「下垂 ≠ 跳回 ROS1」

用户观察：关机后机械臂下垂到最低（正常），**开机后小车因为下垂而「跳回 ROS1」**。
**这条因果链是错的，要拆成两条互不相干的链路。**

**(1)「ROS1 一直在跑」不是回退，是设计如此。**
`start_node.service`（vendor，`enabled`，`WantedBy=multi-user.target`）**每次开机都无条件启动**：

```bash
# /home/pi/armpi_pro/start_node.sh
if [ -f /etc/armpi-ros2/active ]; then
  exec docker exec ... armpi_pro bash /home/ubuntu/armpi_ros2_legacy_sidecar.sh   # ← 走这支
fi
xhost +; docker exec ... source_env.bash .../start_node.sh                        # 完整 ROS1 栈，不走
```

`/etc/armpi-ros2/active` 存在 → 只跑 **legacy sidecar**（roscore + rosbridge **9090** + rosapi +
后置摄像头），**不含 arm/chassis/lidar/IMU/odom**。这是迁移时特意保留的「相机 / 诊断桥」。
`armpi-ros2.service` 同样 `enabled`，两者**并行**启动（`After=docker.service start_node.service`）。
→ **ROS1 从来没被"切回去"过，它是常驻的。**

**(2) 真正杀掉 ROS2 核心的是 LD06 雷达，不是机械臂。**
`arm_node.py` 遇故障只做 `health.fail()` + `on_stop()`（发一次停止报文），**自己并不退出**，
所以 arm 锁存**不会**杀死核心。铁证：**昨天容器里 arm 节点锁存 7 次
（servo 3/5/1/6/1/3/4，均为 `command 9` 通讯类），核心从 13:55 一直跑到 14:58。**

**(3) 但用户的直觉有一半是对的：下垂改变了故障的「性质」。**

| | 臂的位置 | 节点锁存的故障 | 后果 |
|---|---|---|---|
| 昨天 | 935 / 911（**界内**） | `No physical reply from servo N` —— **可恢复的通讯类** | 约 10 秒后自愈 |
| 今天 | **1034（越界）** | `Invalid physical feedback: joint3` —— **不可恢复的越界类** | **永久锁存** |

→ 准确说法：**下垂把「能自愈的故障」升级成了「永久锁存」。**

### 7. ⚠️ 由此暴露「开机自动到位」的架构性缺陷

该功能**在它被设计要解决的场景（掉电）里根本不可能生效**：

> 掉电 → 臂下垂越过 joint3 的 0~1000 → 节点永久锁存 → `reset_eligible` 永远 false →
> 本服务永远等不到可复位窗口，只会 exit 3 或被杀。

首轮（14:49:24）那次"成功"**纯属巧合** —— joint3 = 911 恰好还在界内。

**可选修法（按优先级）：**

1. **(c) 推荐 —— 把回驱挪进启动链路**：在 `armpi-ros2.service` **之前**加一个 oneshot，
   先用总线把 joint3 拉回界内（复用 `tools/joint3_recover.py` 的逻辑），**然后**才启动核心。
   这才是真正解决"掉电后自恢复"。
2. **(d) 必须同时做 —— 隔离雷达**：把 LD06 改成 `required=False` 或独立 launch。
   否则机械臂修好了，雷达一抖照样拖垮核心。**注意这要改容器镜像里的 launch 文件并重建镜像。**
3. (a) 放宽 `JOINTS` 里 joint3 的 high —— 但 `arm_node` 启动时用
   `board.limits(ident) != [low, high]` 断言硬件限位必须一致，改它还得写舵机 `0x30`，风险高，不推荐。
4. (b) 物理防垂 —— 断电时给臂加支撑/垫块，或把臂停在重力稳定位。

### §8 ⚠️ 遗留与必须说清的事

1. **`/run/armpi-ros2/arm-startup-pose.json` 是旧结果**，内容是 `exit_code 137`、`POSE_joint3 = 900`。
   它在 tmpfs 上，**下次运行才会被覆盖** —— 不要把它当成本次结果读。
2. **本轮没有跑过姿态服务。** 用户只要求"读取 + 保存"，未授权动作。**期间未发送任何动作报文。**
   若要验证，`--action run` 会是**零行程空跑**：能证明 gate/auth 链路通，**证明不了行程链路**。
3. **`armpi-startup-pose.service` 当前为 `enabled`**（10-13 就已 enable），意味着**每次开机都会尝试跑**，
   而当前状态是 `failed`。是否保持 enable 需用户决定。
4. **冷启动依旧无效（架构缺陷未动）**：掉电后 joint3 垂到 ≥1034 越界 → 永久锁存 → 服务等不到复位窗口。

   真正的修法仍是 **§「可选修法」第 1 条：在 `armpi-ros2.service` 之前加 oneshot，用总线先把 joint3 拉回界内**。
