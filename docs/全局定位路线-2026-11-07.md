# 全局定位路线（C 方案）· 2026-11-07

## 目标

让车在**断电重启之后**仍知道自己站在哪、脸朝哪边。这样"球在哪"就能记在
一个不会随开机清零的坐标系里，实现用户要的用法：开机发一句抓球指令，车
直接按上次记住的方位去找，不再四个象限盲扫。

## 为什么现在做不到

`ball_memory` 存的 `sighting` 是 **odom 系**的 `(x, y, yaw)` 加距离/方位。
`mecanum_odom` 每次上电从 `(0,0,0)` 重新起算，所以：

- 车被搬动或转过车头 → 存下来的方位指错地方
- `travelled_since` 算出 0 → 漂移惩罚失效，反而过度自信
- 加上 `STALE_AFTER_S=1800`（30 分钟过期）和 `record_outcome(ok=true)` 清空记忆，
  隔夜开机必然是空的

根子是 **D17：没有 SLAM、没有全局定位**。没有 `map` 系就没有跨开机的空间参照。

### 阶段 1 第二次现场尝试 · **成功**（2026-11-07 16:05–16:25）

结论先说：**上次是两处独立故障叠在一起，不是一处。**

#### 故障 A —— 消息过滤器当时确实在丢全部扫描（一次性，不可复现）

按上次列的诊断顺序做完了，**结论是把「tf2 拒绝外插」这条头号嫌疑排除掉**：

| 测了什么 | 结果 |
|---|---|
| 扫描戳 vs 最新 `odom→base_link` 戳 | 扫描恒定新 **+0.042～+0.050 s** |
| 扫描到达时年龄 | +0.001 s（新鲜，不是积压） |
| `odom←base_laser` 在扫描戳上、**零超时** | 在扫描回调里查：**92/92 全失败** |
| 同一查询**推迟 0.3 s** 再查（主循环里，不在回调里） | **103/103 全成功** |
| `odom←base_laser` 用 `latest` | 成功 |

关键在最后两行：**延迟 0.3 s 就能查到**，说明扫描戳并没有超出 TF 未来，只是「扫描刚到的
那 1 毫秒内，覆盖它的那帧 odom TF 还没发出来」。`tf2_ros::MessageFilter` 本来就是靠后续
TF 到达重新检查来补这个的，所以这属于正常时序，不是故障。
（⚠️ 过程教训：v3 探针在**订阅回调里**做阻塞查询，单线程执行器下 TF 进不来，
「等 0.25 s 也没用」是探针自己造的假象。诊断工具不能在回调里阻塞。）

用 `--log-level debug` 跑一次干净会话：**252 条 `Message ready in frame base_laser`，
队列始终为 0，零丢弃**。所以现在过滤器完全正常。上次那批 `queue is full` 是一次
TF 停摆留下的历史状态，那次车在动、Pi 4 负载高，**今天无法复现**。

#### 故障 B —— `check_min_dist_and_heading_precisely: false` 让「纯旋转建图」根本不可能（真正要修的）

`SlamToolbox::shouldProcessScan()`（`slam_toolbox_common.cpp`）原文：

```cpp
const double dist2 = last_pose.SquaredDistance(pose);
if (check_min_dist_and_heading_precisely_) {
    const double heading_diff = fabs(NormalizeAngle(pose.GetHeading() - last_pose.GetHeading()));
    if (dist2 < min_dist2 && heading_diff < min_rotation) return false;  // 都太小才拒
} else if (dist2 < 0.8 * min_dist2) {
    return false;                                                       // 只看位移！
}
```

配置里是 `check_min_dist_and_heading_precisely: false`（模板默认值）→ 走 `else`：
**转角完全不参与判断**，纯原地旋转 `dist2 = 0`，第一帧之后每一帧都被拒。而我们这台车的
建图策略就是原地转圈（旋转里程计准、麦轮直线误差 38%），所以这条路一开始就是死的。

两次实测对照，同一个二进制、同一份参数、同一块地：

| 条件 | 车 | 结果 |
|---|---|---|
| 阈值 `0.10/0.20`、标志 `false`（原配置） | 原地转 **360.1°**，日志零丢弃 | 55 帧 `/map` **一格没长**（free 2114 / occ 119 全程不变） |
| `minimum_travel_distance:=0`、`heading:=0` | **完全静止** | 地图会长（free +1221 / occ +88）← 因为 `dist2 < 0` 恒为假 |
| 阈值 `0.10/0.20`、标志 **`true`** | 原地转 **360.1°** | **free 2124→5846（+3722）、occ 123→365（+242）**，尺寸 117×109→119×110 |

顺带解释上次为什么连「横移 0.2 m」也没用：0.2 m 的 `dist2=0.04 > 0.8×0.01` 本该通过，
它没通过正说明**当时故障 A 还在生效**。两处故障互相掩护，才让人以为是同一个原因。

### 阶段 3 · 改 `ball_memory` 存 map 坐标（**2026-11-07 离线部分已完成**）
- ✅ **`ball_memory.py` 支持按坐标系区分寿命**：
  - `STALE_AFTER_S_BY_FRAME = {'odom': 1800, 'map': 7天}`；默认 `frame='odom'`，
    旧 history 文件没有 `frame` 字段的一律按 odom 处理，**行为完全不变**
  - `predict` / `preferred_heading` 加 `frame` 参数，**不同 frame 绝不混用**
  - `record_outcome(ok=true)` 只清掉 odom 记忆；map 先验保留但置信度 ×0.6
    （球通常会被放回原位，第一次抓成功不该永久烧掉跨开机唯一那条线索）
  - `record_sighting(..., frame='map')` 写 `frame` 字段
- ✅ **`find_and_grasp.py` 加 `--map-frame` 开关（默认关闭）**：
  开启时读 `nav2_amcl` 的 `/amcl_pose` 拿 map 系位姿，用**独立 rosbridge 连接**
  （一条连接订两个话题会互相挤掉消息）。
  `/amcl_pose` 拿不到时 **不退回 odom 冒充 map**，而是不写这条记忆 —— 避免造出
  一个"自信地指错方向"的跨开机记录。
- ✅ 离线验证 42 项全过，其中关键一条：**车被搬动 1 m 后，map 记忆仍算出
  59° 的正确方位**（odom 记忆在这种场景必然指错）。
