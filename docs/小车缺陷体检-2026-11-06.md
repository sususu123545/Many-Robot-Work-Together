# ArmPi Pro 小车缺陷体检报告

**日期**：2026-11-06 13:10
**方式**：**全程只读**。本次没有修改任何文件、没有发送任何运动指令。
**采集手段**：rosbridge（`ws://127.0.0.1:19091`）+ `rosapi` + 仓库静态检查。
**未能覆盖**：系统层（温度、磁盘、systemd、docker）——SSH 22 端口 **连接超时**，见 D3。

---

## 一句话结论

**能力已经跑通，但工程地基是软的。** 抓取链路今天连续成功，可它的代码 **一行都没入库**；
相机帧率只有设计值一半；机器人和导航之间缺一个坐标变换；电量完全不可见。
这些不阻碍"现在能抓球"，但阻碍"明天还能抓球"和"扩展到运水任务"。

| 级别 | 数量 | 含义 |
|---|---|---|
| **P0** | 3 | 会丢东西或让机器人失联，必须先处理 |
| **P1** | 8 | 直接限制能力上限或制造安全隐患 |
| **P2** | 8 | 性能与质量问题，能忍但有代价 |
| **P3** | 2 | 文档与记忆漂移 |

### D2 · 冷启动 joint3 下垂会永久锁存，且没有软件解法

**证据**：历史实测（2026-11-01 起多次复现）。掉电后 joint3 垂到 ≥1034，
超过 `SAFE` 上限 1000，arm 节点进入永久锁存；日志出现
`Invalid physical feedback: joint3`，之后**任何软件指令都被拒**。

**影响**：每次断电重启都可能在开机时就处于不可用状态，只能人工把臂掰回界内。

**现状**：`tools/joint3_recover.py` 能救"轻度越界"，但**救不了开机前就垂下去**的情况——
那时节点还没起来，总线直驱也来不及。真正的解法是"在 `armpi-ros2.service` 之前插一个
oneshot 先用总线把 joint3 拉回界内"，**这个改动一直没做**。

### D3 · 唯一通路是 rosbridge，SSH 已经不可用

**证据**

```
ssh -o ConnectTimeout=6 raspberrypi 'uptime'  →  connect to host raspberrypi port 22: Connection timed out
```

而 `127.0.0.1:19091`（SSH 隧道 → 车上 9091）是通的，`/rosapi/*` 全部有响应。

**影响**：
1. **无法做系统层体检**：CPU 温度、磁盘余量、systemd 单元状态、docker 容器是否健康，全部看不到。
2. **没有带外访问**：一旦 `rosbridge_websocket` 挂掉，机器人即失联，只能手动断电。
   而 rosbridge 是单点——所有工具都挂在它上面。
3. 停车后无法远程确认"是否真的停了"，只能到场看。

**补充**：这不是今天新坏的。历史记录里 11-03 就出现过"认证过、exec 无限挂起"，
当时的结论是"板子开不出进程"。今天表现为 TCP 连接超时，同源。

## P1 · 直接限制能力或制造安全隐患

### D4 · 坐标树缺两块：没有 arm_base，也没有 rear_camera

**证据**（`/tf` 20.2 Hz，`/tf_static` 的发布者是 `base_to_laser` / `base_to_imu`）

```
odom      -> base_link      （动态，mecanum_odom，20.2 Hz）
base_link -> base_laser     （静态）
base_link -> imu_link       （静态）
```

树里**只有这三条边**。而：

- `camera_info` 声明的 `frame_id` 是 **`rear_camera`** —— 树里没有
- 抓取用的是 **`arm_base`** —— 树里也没有

**影响**：
- 任何"用 TF 把视觉结果搬到车体系"的代码都会失败。
- 抓取现在能用，是因为它**绕过 TF**，直接读 `rear_camera_hand_eye.json` 手眼标定文件。
  这等于把标定固化成一个文件，而不是一个可查询的变换。
- 想接 Nav2 / SLAM / 多传感器融合，**这一步必须先补**，否则连"球在哪个坐标系"都答不上来。

**✅ 已修复（2026-11-07）**——注意：本条的原文是对的，但我在 11-06 晚些时候
说过"`/tf_static` 完全为空"，那是**错的**，是 rosbridge 读不到 latch 话题
造成的（见 D16）。到容器里直接 `ros2 topic echo /tf_static` 就能看到两条边。

补的方式：`tools/perception/arm_tf_publisher.py` 作为 sidecar 容器
（`armpi-tf-publisher.service`，`--ipc` 共享核心容器）发布

```
base_link -> arm_base     静态 (0, 0.062, 0.094)，来自 robot_description
arm_base  -> rear_camera  动态 10 Hz，来自手眼标定 + 正解
```

实测查询 `arm_base -> rear_camera` = `[0.003, 0.076, 0.205]`，姿态 pitch
**−122.29°**，与四轴俯仰角之和（47.28 − 91.68 − 77.76 = −122.16°）一致。

⚠️ 顺带查出一个新冲突：URDF 的 `camera_joint`（link4 系 (0, -0.0422, 0.0465)）
与手眼标定推出的 (0.0023, -0.0479, 0.0683) **z 差 21.8 mm**。以手眼为准（8 样本、
RMS 2.46 mm，且据此抓球误差 1.5 mm），URDF 那个值没有出处记录。
`tools/test_arm_tf.py` 把这个 21.8 mm 钉死了，谁修都会立刻失败提醒。

### D5 · 相机实际 4.0 Hz，只有设计值的一半

**证据**（每话题独立连接测量，6 秒窗口）

```
/scan                            10.2 Hz   （设计 10）   ✓
/odom                            20.0 Hz                 ✓
/tf                              20.2 Hz                 ✓
/bmi270/imu_raw                  50.3 Hz   （设计 50）   ✓
/joint_states                     2.2 Hz                 ⚠ 见 D6
/rear_camera/image_raw/compressed  4.0 Hz   （设计 8）    ✗
```

相机本身正常：640×480、`equidistant`、K/D 与标定文件完全一致。

**影响**：
- 抓取的定位融合用 `stability_frames: 5`，8 Hz 时 0.6 s 出结果，**4 Hz 时要 1.25 s**。
- 搜索扫描每步要 `settle`，帧率减半意味着每一步的等待都要相应加长。
- 这是**今天变慢的一个隐性来源**，和 j2 过冲、进程启动无关。

**未查明**：是 USB 带宽、CPU 占满、还是 relay 在限速。需要 SSH 上去看，而 SSH 不通（D3）。

**✅ 已复核、原读数不成立（2026-11-07 11:40）**

按 rosbridge 独立连接直接数消息（工具 `tools/measure_topic_rates.py`），
并核对 header stamp 去重：

```
/rear_camera/image_raw/compressed   12.68 Hz (51 帧 / 4 s，51 个唯一戳，0 重复)
/scan                              10.17 Hz
/odom                              20.20 Hz
/joint_states                       1.99 Hz
```

压缩图现在是 **12.7 Hz，不是 4.0 Hz**。最可能的原因是当时 `web_video_server`
泄漏 MJPEG handler 拖慢了相机；FrameHub 修复 + 11-07 把 `frame_relay` 纳入
systemd 管理后恢复正常。原文的 4.0 Hz 是**特定故障状态下的读数**，不是常态。

⚠️ **测量方法本身有坑**：同一话题用 `ros2 topic hz`（容器内）三次测出
**5.08 / 8.42 / 10.78 Hz**，`ros2 topic info -v /rear_camera/image_raw` 甚至
显示没有发布者。这台车的 DDS 发现被 `ROS_DOMAIN_ID=42` +
`ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST` 限制，ros2cli 从另一个进程订阅
不可靠。**以后测频一律用 rosbridge 独立连接数消息，并查重复戳。**

### D6 · 关节反馈只有 2.2 Hz

**证据**：`/joint_states` 2.2 Hz；`/arm_controller/status` 同为 2.2 Hz（同一次轮询产物）。
6 个关节：`joint1..joint5, r_joint`。

**影响**：
- 每发一条运动指令，**至少要等 ~0.45 s 才可能读到新位置**。这直接解释了为什么
  所有微动都要 `sleep(duration + 0.8)`：0.8 s 不是保守，是**必须**。
- 控制带宽上限被锁死。想提高抓取速度，绕不过这一条。
- 想改善必须先知道控制器在哪轮询——但它的 10 个参数通过 rosbridge 读回来全是 `0.0`
  （类型不匹配，**读数不可信**，见 D14），这条路暂时堵着。

**✅ 根因已查明（2026-11-07）**：不是总线慢，是**定时器写死**。
`arm_node.py:95` 是 `self.create_timer(.5, self.poll, ...)`，即设计值 2 Hz；
实测 1.99 Hz 与之一致。而一次轮询要做 12 次串口往返（5 个臂关节各读
位置+温度，夹爪再读一次），从状态消息里的时间戳量得**只花 0.182 s**，
即每周期有 **0.32 s 空闲**。周期是硬编码，不是参数。

⚠️ **不建议直接调快**：把 0.5 s 改到 0.3 s 会把串口占用率从约 36% 抬到
60%，可能与定时运动指令争总线；而且改 `arm_node.py` 必须走
`DEVELOPMENT.md` 的完整流程（colcon build → pytest → docker commit →
改 core.json 的 image 和 image_id → 重启）。实际收益很小：温度保护 2 Hz 足够，
抓取流程本来就等臂停稳再读，唯一受影响的是运动中的 TF 滞后
（约 0.45 s，按 TCP 30 mm/s 算约 13 mm）。**优先级下调为 P2**，
要做也必须先在真机上 A/B 测运动指令交付率再定。

### D7 · 完全没有电池遥测

**证据**：`/rosapi/topics` 共 **28 个话题，没有任何** `battery / voltage / power / current`。
`/chassis_control/status` 只有 `{dry_run, enable_motion, estop, hardware_fault, wheel_command}`。
`/arm_controller/status` 的 37 个字段里也没有电压或温度。

**影响**：

2. 转向滑移在 **31%–127%** 之间波动，公认与电量相关，却**无法把滑移归因到电压**。
   `turn_to` 只能靠自适应增益硬扛。
3. 今天"边开机边充电"这个状态，**代码完全看不见**，只能靠人告知。

### D8 · 控制台的雷达过滤规则与主流程不一致，且隐藏的正是危险距离

**证据**

| 位置 | 规则 |
|---|---|
| `web_console/sensor_console.html:44` | `r >= 0.3` **一律丢弃** |
| `tools/scan_clean.py` | `>0.08 m` + 四个扇形自遮挡（0–30° / 325–360° / 339–345° / 145–210°） |

控制台第 42–43 行的注释写着"与 `tools/scan_clean.py` 的 `MIN_TRUST_M=0.30` 保持一致"，
但 **`scan_clean.py` 里已经没有 `MIN_TRUST_M` 这个常量了**（`grep` 无结果）。注释是过期的。

**影响**：**操作者用控制台判断"周围有没有东西"，而控制台把 30 cm 内全部抹掉了。**

这条规则本身犯过一次错：11-06 轮胎撞桌角，就是 `scan_clean` 早期版本用同样的
"30 cm 一刀切"把真实桌腿删掉了。主流程后来改成了扇形过滤（保留 30 cm 内**不在自遮挡扇区**
的点），**控制台没有同步**。也就是说：**机器现在的判断比人看到的那张图更准**——
人照着控制台指挥，反而会复现那个错误。

### D11 · 相机装在腕部，球贴到车下就彻底失明

**证据**：检测器 `car_approach.locate_ball` 的面积上限是 8000 px²，

## P2 · 性能与质量问题（能忍，但有代价）

### D12 · j2 小步过冲，方向不对称

**证据**（今日全部 j2 记录）

| 指令 tick | 实际 | 偏差 |
|---|---|---|
| −40 | 45 | **+5** |
| −40 | 44 | **+4** |
| −20 | 25 | **+5** |
| −15 | 20 | **+5** |
| +55 | 47 | **−8** |
| +45 | 37 | **−8** |
| +40 | 32 | **−8** |

规律：**向下多走 3–5，向上少走 7–8**（重力偏差，可建模）。

灵敏度（FK 数值微分，1 tick 对工具点高度的影响）：

| 姿态 | dz/d(j2 1 tick) |
|---|---|
| 搜索姿态 j2=690 | 0.56 mm |
| **贴地 j2=164~200** | **1.28 mm** |

**影响**：贴地时 5 tick 过冲 = 6.4 mm，占 15 mm 地面保护余量的 43%。连续两次必触线。

**注意**：8 月/11-06 上午那轮尝试工具点比 IK 目标低 13.6 mm，其中只有约 5 mm 能由过冲解释，
**剩余约 8 mm 原因未查明**。不要把这个当成唯一根因。
