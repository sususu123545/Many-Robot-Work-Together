## 1. ⚠️ P0 — 安全：机械臂运动门残留为 `true`

### 现象

`/arm_controller/status` 实测状态向量：

```
health_state=RECOVERED_AWAIT_RESET  arm_motion=true  gripper_motion=false
estop=true  reset_eligible=true  feedback_complete=true
```

`enable_arm_motion` 本应是 `false`（`run_native_core.py` 启动时传的是 `enable_arm_motion:=false`），
但有人把它改成了 `true` 且**没有改回来**。

### 根因（已定位）

`armpi-startup-pose.service` 开机执行回位姿态时必须开臂门并解急停 —— 日志原文：

```
20:04:20 systemd: Starting armpi-startup-pose.service ... (OPT-IN: resets the e-stop latch and moves the arm with no human present)
20:04:43 [startup-pose] STEP gate=True arm_gate=True gripper_gate=False estop=False
20:04:43 [startup-pose]   all joints within 12 ticks; stopping
20:04:43 [startup-pose] RESULT reached=True estop=False fault_count=1
20:04:43 systemd: Deactivated successfully
```

它**退出时不回收** `enable_arm_motion`。（`estop` 之所以现在是 `true`，是因为之后又发生了舵机读失败把它重新闩锁了 —— 纯属巧合，不能依赖。）

### 风险

现在是**双重门**（`arm_motion=true` 但 `estop=true`），臂不可动。
**残留的授权应主动收回**。但本镜像 reset 实现会先关闭双门，再确认复位，因此不能把“调用一次 reset”描述为自动授权或自动运动。

### 要做什么

**A. 临时收敛（1 条命令，立即可做，可逆）**

```
ros2 param set /arm_controller enable_arm_motion false
```

| 边界条件 | 说明 |
|---|---|
| 允许设 false | `arm_node.on_set_parameters()` 的健康门**只拦"设为 true"**，设为 false 永远成功 |
| 可逆 | 需要时再设回 true 即可 |
| 影响面 | 无。臂本来就不动，且 `gripper_motion` 已是 false |
| 副作用 | **每次开机都会复发**（因为姿态服务还会再开一次），所以这是临时收敛不是修复 |

**B. 根治（需改文件 + 部署）**

在 `car_setup/ros2/arm_startup_pose_ros.py` 里，让姿态流程**无论成功失败都在 `finally` 中把
`enable_arm_motion` / 相关门恢复为 `false`**；或改为"执行完姿态后显式调用一次带门收回的收尾"。

- 服务名里那句 "OPT-IN: resets the e-stop latch and moves the arm with no human present" 说明这是**有意的设计**，
  所以不要直接删掉开门动作，只补"收尾关门"。
- 修复已部署到 `/opt/armpi-ros2/arm_startup_pose_ros.py`，并更新宿主结果记录脚本。只执行关闭授权分支验证，没有重启 `armpi-startup-pose`；后者会重新回位，需要独立现场确认。

> ⚠️ 在 A 或 B 落地前，**不要把臂的急停解除**（不要调 reset），否则等于把唯一的约束也拿掉。

→ **1034 才是真实下垂静止位**（开机前 joint3 垂到 1034 越界限边缘），bootstrap 每次用 7 条报文把它拉回来。

### ⚠️ 修正一条长期记忆

真相：**joint3 长期在 907 ~ 971 之间浮动**（舵机保持力的平衡点随温度/摩擦变化），
907 只是"某一次的平衡点"。10-14 冻结时看到 907、对比 10-13 的 935，就误判成了"缓存值"。

### 要做什么

**不需要紧急处理**，但要知道两件事：

1. **下次开机会真的动 joint3**：偏差 28 > 容差 12 → `armpi-startup-pose` 会往内推 28 个脉冲。
   28 < `MAX_TRAVEL=400`，在安全范围内，但**开机时臂周围不能有人/障碍物**。
2. **更新文档表述**：`car_setup/ros2/arm_startup_pose.json` 里那份 `target_raw` 与实测"逐位相等 → 行程为 0"的
   说明已经过时，应改成"joint3 会在 907~971 间浮动，偏差超过容差 12 时姿态服务会主动拉回"。
   **target 值 907 本身建议保留**（它距 1000 限位有 93 tick 余量，是偏保守的值）。

## 3. P2 — 舵机读失败约 0.084%，原因尚未排除硬件/固件/时序

### 现象

核心日志持续刷屏：

```
[arm-4] [ERROR] Arm feedback fault (latched): No physical reply from servo N, command 9 after 3 reads
[arm-4] [INFO]  Arm health: READ_ERROR → RECOVERING → RECOVERED_AWAIT_RESET
```

`N` 在 1 / 2 / 3 / 5 / 6 之间轮转，约每 10 秒一轮。

### 数据（两个时间点）

| 时刻 | requests | read_success | attempt_timeout | read_timeout |
|---|---|---|---|---|
| 20:31 | 37816 | 37785 | 333 | 31 |
| 20:34 | 42886 | 42850 | 387 | **36** |

→ **42886 请求 / 36 次"三次全败" = 0.084%**，`read_success` 占 99.92%。

### 诊断计数（不足以排除硬件故障）

| 指标 | 实测 | 能说明什么 / 限制 |
|---|---|---|
| `crc_error` | **无** | 已收到帧未记录 CRC 错误；不能分析完全没收到的回包 |
| `resync`（`discarded_bytes`） | **无** | 未记录失步，不能排除接线/电气造成的丢包 |
| `reply_queue_overflow` | **无** | 未记录队列溢出，不能据此排除全部时序问题 |
| `receiver_error` | `null` | 当前未记录接收线程异常 |
| 回复延迟 | 成功样本 **2.1 ~ 2.9 ms** | 不包含超时失败样本，不能代表其延迟或原因 |
| 失败命令 | **`command 9`（读温度）** | 此轮未记录 `command 5`（读位置）失败；不代表未来不会失败 |
| 重试 | **有效** — `query_id 42498` servo 6 cmd 9：attempt 1/2 超时 → **attempt 3 成功（2.794 ms）** | — |

→ 目前只确认存在无应答；不能据此认定只是廉价舵机噪声，或宣称无需检查硬件。

### 真正的问题

**每次"三次全败"都会把整个臂闩锁成 `READ_ERROR` 并要求人工 reset。** 可用性受到影响，但改变策略前必须保留反馈失效时的运动抑制。

### 要做什么（需改代码 + 重建镜像）

原“连续 3~5 次失败才锁存”的建议**暂不实施**。先定位温度查询无应答原因，再设计并验证容错；不能仅依据低失败率，让反馈失效时继续允许运动。

> 边界：本次没有修改 `arm_health.py`、急停语义、限位/温度阈值或动作前校验。

## 6. 已知陷阱（踩过的坑，别再踩）

1. **镜像 `src/` ≠ 运行时代码** —— 一律以 `/opt/armpi_ros2/install/` 为准（见 §4）。
2. **`echo ##SRC` 在 bash 里是注释** —— `#` 位于词首即为注释，会吞掉整行。用 `@@SRC@@` 之类的标记。
3. **`armpi_pro` 已停止** → `docker exec armpi_pro` 必然失败，会被误读成"文件不存在"。要用 `docker cp`；
   而 `docker cp armpi_pro:/home/ubuntu/.` 实测**会卡住 >60 秒**，慎用。
4. **小车换 IP 后 `known_hosts` 里查不到新 IP** —— 但 `connect(key_alias='raspberrypi')` 能兜住，别急着重新信任主机键。
5. **判断重启只认 `/proc/uptime`** —— Pi 无 RTC，`docker ps` 的 "Up N hours" 与 systemd 的 "since Nh ago" 都会偏。
6. **判断臂是否被软件控制看 `fuser -v /dev/rrc`**，不要只看服务名。
7. **`tools/runtime/` 是 git-ignored** —— 凭据文件（`arm_creds.json`）和一次性诊断脚本放这里**不会**进公开仓库；
   反之**要入库的脚本绝不能放这里**，会被静默忽略。
