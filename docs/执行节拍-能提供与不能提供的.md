## 3. 节拍边界：源码可查，不需要 bag

虽然没有实测记录，但**上下界是代码里写死的**：

| 项 | 值 | 出处 |
| --- | --- | --- |
| **六轴反馈频率** | **2.0 Hz**（每 0.5 s） | `armpi_ros2/arm_node.py:99` `create_timer(.5, self.poll)` |
| 读一次反馈的耗时 | `drain(0.3)` + 等下一帧 0~0.5 s | `grasp_sequence.py:265-266` |
| 单条 jog **声明**时长 | **1.5 s** | `jog_ex(duration=1.5)` |
| jog 之后固定等待 | **+0.8 s** | `time.sleep(duration + 0.8)`（`:593`） |
| 单条 jog 端到端 | **≈3.0 ~ 3.6 s** | 读 0.3~0.8 + 声明 1.5 + 等 0.8 + 再读 0.3~0.8 |
| **脚本实际指令节拍** | **≈0.28 ~ 0.33 Hz** | 1 / 3.3 s |
| 总线允许的最短命令 | 0.3 s → 3.33 Hz | `spec.MIN_MOVE_DURATION_S` |
| 单条命令行程上限 | 100 tick = 24° | `spec.DEFAULT_MAX_STEP_TICKS` |

由此可推（**这是推算，不是实测**）：56 条 jog × ≈3.3 s ≈ **185 s ≈ 3 分钟**，
仅 jog 阶段；再加上视觉、IK、约 10 次 `reset_estop` + 门控重设、夹爪开合，
那次抓取的墙钟时间应在 **4~5 分钟**量级。

## 4. 这条结论修正了我上一版的说法

我在 [阻断项文档](./仿真策略上真机的阻断项-2026-11-23.md) §B5 里写「帧率差 **3 倍**」，
那是按**总线命令上限 3.33 Hz** 算的。**这个算法不对。**

真正卡住的是**观测**：

- 策略要闭环，就得看到结果；六轴反馈只有 **2 Hz**；
- 所以真机的**观测天花板 = 2 Hz**，与总线能发多快无关；
- 训练用的数据是 **10 fps** → 差 **5 倍**，不是 3 倍。

而且 10 fps 数据里相邻 5 帧的差异，在真机上**根本看不到**——那部分信息是训练时有、
执行时不存在的。

## 5. 下次能采到什么（工具已就绪）

```bash
# 只订阅 /joint_states，不发布、不动运动闸门，空载也能跑
python3 tools/capture_cadence.py listen --seconds 60 --out cap.jsonl
```

输出两件东西：

- `cap.jsonl`：每行 `{t_wall, t_mono, header_stamp, ticks{joint1..r_joint}}`
- `cap.summary.json`：实测频率、间隔 min/median/mean/p95/max、`header_stamp − 到达时刻` 的平均偏差、
  以及哪些关节从未出现

这一条能给的是**反馈侧**的真实节拍（实测 vs 源码的 2 Hz 是否一致、抖动多大）。

**目标侧**（命令时刻 + 目标 tick + 前后反馈）需要在动臂时同录。
命令已经写好，但**动臂必须你在场**，建议下次会话跑一段 3 步单关节 jog，
每次只走 20 tick，全程在窗口内。

## 6. 需要确认两件事

1. **要不要安排一次带时间戳的运动采集？** 代价：你真机在线 + 约 2 分钟；
   收益：拿到"目标 ↔ 反馈"配对，节拍从推算变成实测。
2. **反馈 2 Hz 这个天花板，仿真组是否接受作为训练帧率上限？**
   如果不接受，就得先改车上 `arm_node.py` 的轮询定时器——那是另一件事，
   而且会加重舵机总线负载（当前 12 次串口往返只用 0.182 s，但频率翻倍会与命令争总线）。
