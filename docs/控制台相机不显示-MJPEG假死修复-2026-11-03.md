# 控制台相机：黑屏 / 帧率骤降 的根因与修复 — 2026-11-03

## 一、现象

1. 网页控制台里**雷达正常、相机画面一直不出图**；
2. 修好后相机能动，但**帧率只有个位数**（用户记忆里之前是 15–20 Hz）。

## 二、定位过程

| 检查 | 结果 |
|---|---|
| 雷达 | rosbridge（本机 9090 → 车上 9091）正常，`/scan` 有数据 |
| 相机链路 | 页面 → 代理 `/stream` → 车上 `8080` web_video_server |
| 车上 8080 `/snapshot` | **超时**（无响应） |
| 核心容器进程 | `web_video_server` **CPU 100%**、累计 CPU 8 分钟，`/snapshot` 不响应 |
| 主机侧连接 | 代理进程对 `小车:8080` 有 **20+ 条 `FIN_WAIT_2`** 半关闭连接 |
| 整机负载 | load average **6.08**（4 核），相机节点被 CPU 挤到只有约 6 Hz |

根因分两层：

- **黑屏**：`web_video_server` 的 MJPEG handler 在客户端中断后**不会退出**。旧页面用
  `fetch('/stream')` 读 MJPEG，超时/刷新就重连，每次重连泄漏一个服务端 handler；
  积压后该进程 100% CPU 假死，8080 不再响应（雷达走 rosbridge 所以不受影响）。
- **低帧率**：假死进程把整机 CPU 吃满（load 6+），相机/USB/网络全被拖慢；
  清掉后帧率恢复到相机自身水平。**相机帧率 = min(相机模式上限, 1/曝光时间)**，
  自动曝光在弱光下会拉长曝光、帧率随之下降（见下表）——这是物理限制，不是软件问题。

## 三、最终方案（已落地，防复发）

```
相机(v4l2_camera) → /rear_camera/image_raw/compressed (JPEG, 相机帧率)
        ↓ 订阅
车上 frame_relay（systemd: armpi-frame-relay，容器 frame_relay，:8099）
        ↓ 一条稳定 HTTP 流
主机代理 FrameHub（proxy_server.py，缓存最新帧，提供 /frame + /api/video）
        ↓
网页 sensor_console.html（/frame 高频轮询 ~14 次/秒，显示帧率 = 相机帧率）
```

| 文件 | 作用 |
|---|---|
| `tools/perception/frame_relay.py` | 车上取帧服务：订阅压缩图并供 HTTP（`/frame`、`/stream`、`/health`），对客户端断开免疫 |
| `tools/perception/armpi-frame-relay.service` | systemd 单元：随 `armpi-ros2` 启停（`PartOf`）、开机自启、自动等核心容器并共享其 IPC |
| `web_console/proxy_server.py` | `FrameHub` 维持**唯一**上游连接并缓存最新 JPEG；`/frame` 供页面高频取帧；8080 `/snapshot` 仅作一次性兜底 |
| `web_console/sensor_console.html` | 相机改为 `/frame` 轮询（`CAMERA_POLL_MS=70`），不再用 MJPEG 长连接 |

关键点：**车端视频服务只看到代理这一个长期稳定客户端**，页面刷新/断开永远不会泄漏车端 handler。

## 四、帧率的真实决定因素（实测）

| 时间/条件 | 曝光 | 实测帧率 | 画面平均亮度 |
|---|---|---|---|
| 13:57（开灯） | 自动（短） | 12–19 Hz | 101.8 |
| 14:20（关灯） | 自动（拉长到 ~160 ms） | 6.3 Hz | 5.1 |
| 强制 10 ms 曝光（关灯） | 10 ms | 19.2 Hz | 0.7（几乎全黑） |
| 强制 160 ms 曝光（关灯） | 160 ms | ~6 Hz | 5.3 |

结论：**关灯后帧率只有个位数是相机用曝光换亮度的物理结果**。
软件链路已做到“相机出多少帧就显示多少帧”（relay 的 seq 增长速率与容器内 publisher 速率一致）。

## 五、操作命令

```bash
# 亮度优先（默认）：自动曝光；开灯后帧率自然回到 12~19 Hz
ros2 param set /rear_camera/camera auto_exposure 3

# 帧率优先（弱光下画面会明显变暗）
ros2 param set /rear_camera/camera auto_exposure 1
ros2 param set /rear_camera/camera exposure_time_absolute 100   # 单位 100 us -> 10 ms
```

车端自检：

```bash
systemctl is-active armpi-frame-relay
curl -s http://127.0.0.1:8099/health      # seq 在增长、age 很小即正常
```

主机自检：

```bash
curl -s http://127.0.0.1:8000/api/video   # connected=true 且 frames 在增长
```

恢复手段（仅在车端视频服务再次异常时）：`sudo systemctl restart armpi-ros2`
（frame_relay 会随 `PartOf` 自动重启；视觉侧车 `grasp_perceiver` 需手动重启）。

## 六、以后如何避免

- **不要**再用 MJPEG 长连接拉相机（旧 `web_console/robot_console.html` 的 `<img src=/stream>`
  是同类隐患）；控制台页面已改用帧总线。
- 相机不出图时：先 `curl http://<小车IP>:8099/health`，再 `curl http://<小车IP>:8080/snapshot?...`；
  前者正常说明车端取帧正常，看代理 `/api/video` 与页面；后者超时说明 web_video_server 异常。
- 页面更新后浏览器 **Ctrl+F5 强制刷新**。
- **关灯/弱光会直接降低相机帧率（曝光换亮度）**；需要高帧率就开灯，或切到“帧率优先”模式。
