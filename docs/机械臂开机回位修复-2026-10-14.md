# 2026-10-14 机械臂开机回位修复

## 直接原因

在 `192.168.55.178` 只读订阅真实驱动诊断，ID 4 的位置报文为
`04 05 00 01 04`：返回状态 0，位置为小端有符号值 `0x0401 = 1025`。
温度约 25°C，接收线程没有错误；不是“界面显示 980 所以实际也是 980”。
980 是数分钟前最后一次完整有效反馈的缓存。

关节 3 的命令限位仍为 0～1000。下垂后实际位置超过这个范围，正常驱动
持续锁存错误，原开机客户端反复等待复位，但不能完成回位。

## 修复边界

- 不修改正常驱动的 0～1000 命令限位、温度保护或人工急停逻辑。
- 用户明确确认运动路径畅通、人员离开关节范围并在旁可急停，才进行本次实车动作。
- 新增 `arm_bootstrap.py`，由原生核心启动器在普通驱动之前调用。
- 功能仅在保存姿态配置明确启用时工作，每次系统启动最多自动执行一次；
  同一次开机的服务重启不重复自动恢复，失败记录也不自动清除或重试。
- 引导程序只独占 `/dev/rrc`，只向关节 3（ID 4）发送向内的位置命令。
- 位置超过 1040、低于合法下限、硬件限位不符、温度达到 55°C、
  反馈不稳定、反向移动或通信失败，均不继续动作。
- 普通每步最多 25 脉冲、1.5 秒；首次从小幅越界进入合法命令范围时最多 40 脉冲。
  最多 12 条位置命令，所有命令目标仍在 0～1000 以内。
- 不只是“回到 1000 附近”：向用户已保存的关节 3 目标 907 回收，保留上限余量。
  已在目标附近或更低的合法位置，不执行引导动作，交由正常回位流程处理。
- 正常回位采用最多 25 脉冲/步、1.5 秒，等待连续健康反馈后才授权。
  人工急停不能被开机客户端清除；回位途中出错，不自动复位续跑。
- 修复 `NOT_READY` 被字符串包含判断误认为 `READY` 的问题。
- 修复读取旧缓存后继续动作/误报到达的风险，使用完整、及时的真实反馈。

这不是任意未知位置下的无条件回正功能，也不证明所有不同姿态间的路径无碰撞。

## 实车验收

1. 首次仅恢复到合法范围：1025 → 1007 → 997，26～27°C。
   随后实测缓慢漂移到 1002，因此仅进合法范围不算完成修复。
2. 余量修正：1002 → 985 → 969 → 955 → 938 → 920 → 915，6 条低速命令，31～34°C。
3. 完整 ROS2 回位客户端返回 `ok=true`、退出码 0、`reached=true`。

| joint1 | 483 | 483 | 0 |
| joint2 | 686 | 681 | 5 |
| joint3 | 907 | 916 | 9 |

允许误差为 12 脉冲，不是精确到同一脉冲。夹爪保持 100，没有参与回位。
回位后 25 秒观察：最新 READY、完整反馈、无新增故障；joint3 约 915，
底盘禁用且四轮指令全零，夹爪禁用，雷达约 9.92 Hz。

`armpi-ros2`、`armpi-startup-pose` 均已启用开机启动。
本次是受限实车动作及服务启动流程验收，未进行完整断电／重新开机验收。
本次开机的 bootstrap 记录仍对应较早的 998 无动作测试；新版 907 余量逻辑
通过的是独立实车试验和同一次开机的回位客户端验证，不能混称为冷启动验证。

```bash
systemctl status armpi-ros2 armpi-startup-pose --no-pager
sudo cat /run/armpi-ros2/arm-bootstrap.json
sudo cat /run/armpi-ros2/arm-startup-pose.json
journalctl -u armpi-ros2 -u armpi-startup-pose -b --no-pager -n 60
```

回位服务成功后显示 inactive 是 oneshot 的正常行为，须看 `Result=success`
与结果文件，不要仅以 inactive 判断故障。备份不要在程序占用硬件时直接覆盖／重启。
