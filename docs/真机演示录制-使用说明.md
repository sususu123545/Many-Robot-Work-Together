# 真机演示录制：使用说明

工具：`tools/record_demo.py`（19 项测试）。2026-11-23 新增。

---

## 它解决什么

`grasp_sequence.py` 会取帧、会读关节，但**两样都不留**——一次成功抓取的唯一产物是控制台那行
`RESULT`。所以真机到现在为止，**一条可训练的样本都没有**。

这个录制器在旁边旁听，把「图像 + 六轴 + 当步下达的目标」存成样本。
**它不发布任何消息、不碰运动闸门、开自己的连接**，所以不会挤占控制回路的读取。

## 为什么是 2 Hz，不是 3.33 fps

不是我选的，是真机限制的：

| 来源 | 频率 | 出处 |
| --- | --- | --- |
| `/joint_states` | 2 Hz | `arm_node.py:99` 的 0.5 s 定时器 |
| `/arm_controller/status` | 2 Hz | 同一个定时器 |
| 腕部压缩图像 | ≈12.7 Hz | 相机节点 |

所以**臂状态天然只有 2 Hz**。录成 3.33 fps 会造出一个现场根本不存在的节奏，
训出来的策略在执行时必然对不上。图像按原生 12.7 Hz 存，事后按时间戳配到状态上。

**2 Hz 就是闭环执行时的观测天花板**，录这个速率是诚实的。

## 怎么用

开两个终端（都要先起隧道：`python tools/ssh_tunnel.py --host 100.102.57.19`）。

**终端 1：先起录制**

```bash
python tools/record_demo.py run --out-dir recordings/demo_01 \
  --task "Pick up the red ball." --seconds 420
```

**终端 2：再跑抓取**

```bash
python tools/grasp_sequence.py
```

抓取结束后回终端 1 按 `Ctrl-C` 提前收尾（否则会等满 420 s）。抓取成功那次墙钟约 4\~5 分钟，
所以 420 s 是合理的上限。

## 实测（2026-11-23 真车，rosbridge 经隧道）

录制器已在真车上跑通。两种取图模式的实测：

| 模式 | 状态频率 | 图像 | 配对率（50 ms 内） | 中位偏差 |
| --- | --- | --- | --- | --- |
| `--image-throttle-ms 100`（**默认**） | **1.85 ~ 2.02 Hz** | ~8~9 Hz | 86 ~ 94% | 25~27 ms |
| `--image-throttle-ms 0` | 1.68 ~ 1.71 Hz | ~16 Hz | **100%** | 14~16 ms |

**默认为什么是 100 ms**：臂状态按构造就是 2 Hz，录不满 2 Hz 意味着训练数据里**本来就没有的采样点**。
不限流时每帧都要解码落盘，16 Hz 的图像会把单线程循环压死，状态流掉到 1.7 Hz；
改成**让 rosbridge 服务端少发**（而不是收到再丢），状态就能回到 1.85~2.02 Hz，配对仍保 86~94%。

⚠️ `--min-image-interval` 是**客户端丢弃**，会把状态流压到 1.35 Hz、配对掉到 51%。别用。

证据：`artifacts/recorder_bench_20261123/`（两份真实 meta + bench 汇总）。

## 它写什么

```
recordings/demo_01/
  meta.json            # 起止时间、话题、两个消息计数、是否发布过任何东西、汇总
  task.txt             # 语言指令原文
  arm_states.jsonl     # 每行一条样本状态
  images/index.jsonl   # 每行一张图：文件名、stamp_ns、字节数、sha256
  images/000001.jpg …  # 原始压缩图像字节，未重编码
```

`arm_states.jsonl` 一行长这样：

```json
{"t_mono": 12.4, "stamp_ns": 1795415352527473934,
 "ticks": {"joint1": 484, "joint2": 687, "joint3": 931,
           "joint4": 206, "joint5": 499, "r_joint": 247},
 "last_command": {"sequence": 2, "accepted": true,
                  "joint_names": ["joint3"], "targets": [[4, 907]]},
 "temperature": {"joint1": 27, ...},
 "tf_arm_base_to_rear_camera": {"stamp_ns": ..., "xyz": [...], "quaternion_xyzw": [...]}}
```

### action 标签的语义（重要）

`last_command` 是 **arm 节点回显的最后一条被接受的命令**，不是调用者的意图。
这是真机上唯一诚实的动作标签来源，转换器不会把它"美化"成意图。

## 收工必查

```bash
python tools/record_demo.py verify --dir recordings/demo_01
```

判据（任一不过就判不可用，退出码 1）：

| 检查 | 阈值 |
| --- | --- |
| 每条样本都有六轴 | 必须 |
| 每条样本都带目标 | 必须（否则数据集没有动作标签） |
| 图像数 | ≥2 |
| 状态↔图像配对率 | ≥90%（50 ms 内） |
| 状态流最长断档 | ≤2 s |

`pairing` 那一行的中位偏差是现场能不能用的直接指标。**如果配对率低，先查图像流**，
不要急着导数据集。

## 还没做的一步

录制器只产出**原始记录**，还没有转成 LeRobot 数据集。

拆分原因：本机（Windows）没有 `lerobot`/`torch`，转换必须在 ycw 上跑，
这与现有的 `t07_convert_remote.py` 一致。下一步是一个转换脚本，做四件事：

1. 按 `stamp_ns` 把每张图配到最近的状态；
2. `observation.state` = 六轴 tick（或换算成弧度）；
3. `action` = `last_command.targets` 展开成六维（缺的关节沿用当前读数）；
4. 按 `fps=2` 写 LeRobot v3 数据集，并像 `t07_convert_remote.py` 一样读回来验证形状。

## 局限，必须知道

- ⚠️ **车上的 status schema 已经变了，和 11-23 那批记录不是同一套。**
  旧版：`arm_message_ns`（顶层）、`joints`、`last_command`；
  现在跑的这版：`stamp.{sec,nanosec}`、`arm_joints`、`last_command_result`。
  解析器**两种都认**（`capture_pose_sweep._parse_status`），否则会静默产出零样本——
  这个坑我踩过一次。
  **推论**：11-23 那 21 份 `capture_report.json` 反映的是**当时的节点版本**，与现在跑的不是同一个二进制。
- **未做真机抓取验证**：只验过 25 秒的被动录制，没有一边抓球一边录。
  第一次正式录建议先 `--seconds 30` 短录，用 `verify` 确认「六轴齐 / 有目标 / 配对率达标」。
- 只覆盖**腕部单视角**，没有侧视，所以「球是否离地」仍然无法从数据里证明。
- `last_command.targets` 是 `[[舵机ID, tick], ...]`，可能只包含本条命令动的那个关节；
  转换器需要"未出现的关节沿用当前读数"这条规则，不能当成六维全量。
- 状态样本来自 `/arm_controller/status`；`/joint_states` 只计数不存储，避免同一时刻存两份。
  若 `verify` 报「no state carried a commanded target」，先查 status 话题是否在发。
